# Authentication API

All endpoints prefixed `/api/auth/`. Require `x-tenant-id` header on localhost.

---

## POST /api/auth/login

Password-based login.

```http
POST /api/auth/login
Content-Type: application/json
x-tenant-id: acme

{
  "email": "user@example.com",
  "password": "secret"
}
```

**Response — success (no MFA):**

```json
{
  "accessToken": "eyJhbGciOiJSUzI1NiJ9...",
  "refreshToken": "...",
  "user": {
    "id": "uuid",
    "email": "user@example.com",
    "firstName": "Ada",
    "lastName": "Lovelace",
    "tenantId": "tenant-uuid"
  }
}
```

**Response — MFA required:**

```json
{
  "mfaPendingToken": "...",
  "methods": ["totp", "backup"]
}
```

**Errors:** `401` invalid credentials · `403` account disabled · `429` rate limited

## POST /api/auth/register

Create a new user account in the tenant.

```http
POST /api/auth/register
Content-Type: application/json
x-tenant-id: acme

{
  "email": "newuser@example.com",
  "password": "StrongPass123!",
  "firstName": "Ada",
  "lastName": "Lovelace"
}
```

**Response `201`:**

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "user": { "id": "uuid", "email": "newuser@example.com" }
}
```

The password is checked only against the tenant password policy (minimum length, common-password list,
repetition, must not contain the email). There is no forced uppercase/digit/symbol rule; passphrases are fine.

**Errors:** `409` email already exists · `400` password violates the tenant password policy

---

## POST /api/auth/logout

Revoke the current session.

```http
POST /api/auth/logout
Authorization: Bearer <access-token>
```

**Response `204`:** No content

---

## POST /api/auth/refresh

Exchange a refresh token for a new access token + refresh token pair.

```http
POST /api/auth/refresh
Content-Type: application/json

{
  "refreshToken": "..."
}
```

**Response `200`:**

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "..."
}
```

**Errors:** `401` invalid / expired / reused refresh token (reuse revokes entire family)

---

## POST /api/auth/magic-link

Send a passwordless login link to the user's email.

```http
POST /api/auth/magic-link
Content-Type: application/json
x-tenant-id: acme

{
  "email": "user@example.com"
}
```

**Response `202`:**

```json
{ "message": "Magic link sent to your email" }
```

Rate limited: 3 per 10 minutes per email.

## POST /api/auth/magic-link/verify

Consume a magic link token.

```http
POST /api/auth/magic-link/verify
Content-Type: application/json
x-tenant-id: acme

{
  "token": "a3f9c2d1..."
}
```

**Response `200`:**

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "user": { ... }
}
```

## POST /api/auth/forgot-password

Always answers `200`, whether or not the account exists. For a known account two emails are sent: a
single-use **link** (valid 60 minutes, purpose-bound, stored hashed, a newer request supersedes it)
and a 6-digit **code** (fallback, 15 minutes). Optional `redirectUri` (see below).

```http
POST /api/auth/forgot-password
{ "email": "user@example.com", "redirectUri": "https://app.acme.com/welcome" }
```

## GET /api/auth/reset-password/validate?token=

Non-consuming check (safe for email scanners / page loads). `200`:
`{ "valid": true, "expiresInSeconds": 3120, "redirectUri"?: "..." }`. Otherwise `410 LINK_EXPIRED`,
`409 LINK_ALREADY_USED` or `401 AUTH_TOKEN_INVALID`. The response never contains the account.

## POST /api/auth/reset-password

Either the link token or email + code. A rejected password (`422`) leaves the link usable. Success
revokes every session of the account, spends any other outstanding link / code, and returns
`{ message, redirectUri? }`.

```http
POST /api/auth/reset-password
{ "token": "<from the link>", "password": "NewStrongPass123!" }
{ "email": "user@example.com", "otp": "123456", "password": "NewStrongPass123!" }
```

## Link failure states

verify-email, magic-link/verify, reset-password(+validate), invite/validate and invite/accept answer
with distinct stable codes: `LINK_EXPIRED` (410), `LINK_ALREADY_USED` (409), `AUTH_TOKEN_INVALID`
(401, unknown) or `INVITE_INVALID` (400, unknown invitation). `LINK_WRONG_ACCOUNT` (403) is reserved
for links bound to a different account.

## redirectUri on email links

`magic-link/send`, `forgot-password` and `resend-verification` accept an optional `redirectUri`. It must
be an exact redirect URI of one of the workspace's OAuth clients or a URL on the portal / frontend
origin; otherwise `422` (checked before the account is looked up). It is stored with the token and
returned by `magic-link/verify`, `reset-password/validate`, `reset-password` and `verify-email`.

## Cross-device magic link (number matching)

`POST /api/auth/magic-link/send { email, poll: true }` returns
`{ message, expiresInSeconds, pollingNonce, matchCode }`. Both values are returned for unknown emails
too and only to the requesting device; neither is in the email. Show `matchCode` (6 digits) on that
device.

- `GET /api/auth/magic-link/preview?token=` (non-consuming): `{ requestedFrom: { userAgent, ip } | null,
  requiresMatchCode }`. `userAgent` is coarse ("Chrome on macOS"). Use it on the confirmation screen
  ("Sign-in requested from ... "). Errors: `410 LINK_EXPIRED`, `409 LINK_ALREADY_USED`, `401`.
- `POST /api/auth/magic-link/verify { token, matchCode? }`
  - **without** `matchCode` (ordinary click): signs in the clicking device as before AND voids the
    pending cross-device request, so a poll can never complete from a plain click.
  - **with** the correct `matchCode`: the link is spent, the confirming device gets **no session**
    (`{ "status": "confirmed-on-other-device" }`) and the polling device may now complete.
  - wrong code: `401 AUTH_OTP_INVALID`, the link is not spent; after 5 wrong codes the request is void.
- `POST /api/auth/magic-link/poll { pollingNonce }`: `{ "status": "pending" }` until confirmed, then once
  the same response as verify (cookies / MFA challenge / enrollment); again: `409 LINK_ALREADY_USED`.

Tenant-bound, 10 minute lifetime, codes and nonces stored hashed, constant-time comparison.

## Invitations

`POST /api/auth/invite/request-new { token }` (invitee holds an expired link): mails a fresh link to the
invited address and replaces the old one; `429` with `retryAfterSeconds` inside a 10 minute cooldown;
`409 LINK_ALREADY_USED` if accepted. `POST /api/auth/invite/accept` now also returns
`canSignInNow: true`.
