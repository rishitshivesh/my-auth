# API Reference

Live interactive docs (Swagger UI) are available at `http://localhost:4000/api-docs` when running in development mode.

## Base URLs

| Environment | URL |
|-------------|-----|
| Local dev | `http://localhost:4000` |
| Production | `https://api.sentry.scrolloop.com` |

## Authentication

All authenticated endpoints require a Bearer token in the `Authorization` header:

```http
Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6Ii4uLiJ9...
```

Tokens are RS256-signed JWTs. Verify them using the tenant's JWKS endpoint:

```
GET /.well-known/jwks.json
```

## Tenant context

Most endpoints require the tenant to be resolved. On localhost (no subdomain), pass the tenant slug via header:

```http
x-tenant-id: acme
```

In production with subdomain routing, the tenant is resolved automatically from the hostname.

## Response envelope

All responses are wrapped:

```json
{
  "data": { ... },
  "meta": {
    "timestamp": "2024-01-01T00:00:00.000Z",
    "requestId": "uuid"
  }
}
```

Paginated responses include:

```json
{
  "data": [...],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 142,
    "totalPages": 8
  }
}
```

## Request IDs and error shape

Every response carries an `x-request-id` header. Send your own `x-request-id` matching
`/^[A-Za-z0-9._-]{8,64}$/` to correlate calls; anything else is replaced with a generated UUID.

Successful responses use the `{ "status", "data" }` envelope. Every error is returned as
[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details with
`Content-Type: application/problem+json`:

```json
{
  "type": "urn:scrolloop:problem:VALIDATION_FAILED",
  "title": "Validation failed",
  "status": 422,
  "code": "VALIDATION_FAILED",
  "detail": "One or more fields are invalid.",
  "requestId": "3f1c9a52-8e7b-4d0a-9c11-2b6f5e0d7a41",
  "errors": [{ "field": "email", "message": "email must be a valid email" }]
}
```

| Field | Type | Always present | Description |
|-------|------|----------------|-------------|
| `type` | string | yes | `urn:scrolloop:problem:<code>` |
| `title` | string | yes | Short, stable, human-readable summary |
| `status` | number | yes | HTTP status |
| `code` | string | yes | Stable machine code from the table below. Branch on this, not on `title` or `detail` |
| `detail` | string | no | Safe to show a user. Never reveals whether an account exists |
| `requestId` | string | yes | Quote this when reporting a problem; also in the `x-request-id` header |
| `errors` | `{ field, message }[]` | `VALIDATION_FAILED` only | Per-field messages; `field` is a dotted path |
| `retryAfterSeconds` | number | `RATE_LIMITED` only | Mirrors the `Retry-After` header |

Quote the `requestId` when reporting problems; it can be searched with the
[audit log](/docs/api/audit) `requestId` filter.

> **Note:** OAuth 2.0 (`/oauth/*`) and SCIM (`/scim/*`) protocol endpoints keep their native error formats
(RFC 6749 `{ "error", "error_description" }` and RFC 7644 SCIM errors) so standard clients keep working.

## Rate limits

| Endpoint group | Limit |
|----------------|-------|
| Auth (login, register) | 5 req / 15 min / IP |
| Magic link | 3 req / 10 min / email |
| Tenant registration | 3 req / hour / IP |
| Setup token | 5 req / min / IP |
| General API | 100 req / min / user |
