# Product screens and UX completion checklist

This is the temporary delivery checklist requested by the project owner. Delete it only after the entire design and flow coverage is finished. It is deliberately kept in the docs app.

## Working agreement

- Assume the backend is working. Focus this work on screen design, UX and integration flows; backend repairs are outside this design task.
- Every implemented API must map to a human-facing screen/action, an external protocol step, or an operational output. Do not force machine endpoints into individual pages.
- Missing product features are included in design scope, labelled **Proposed capability** in handoff annotations. Missing APIs do not stop their screen design and do not appear as technical blockers in the product UI.
- Track screen design, prototype coverage, API mapping and frontend implementation separately. A checked screen does not mean an implemented or tested application flow; state, responsive, prototype and implementation checks remain independent.
- Destination: [Scrolloop Sentry — Product Design](https://www.figma.com/design/fRxM0xxiZ0VN7JQdISP2kb), Rishit Shivesh’s Team.

## Visual direction

A modern identity workspace: quiet warm-neutral canvas, precise typography, mint used intentionally, strong contextual navigation, spacious content, compact readable tables, restrained borders/shadows and purposeful motion. Preserve Montserrat / DM Sans / JetBrains Mono; use editorial display sparingly and clear sentence-case labels. Prioritize progressive disclosure, useful defaults, search/filter affordances, inline validation, clear next steps and reversible drafts. Keep personal security separate from organization policy and platform operations.

- **222 editable screen frames** now cover all **61 inventoried families** (47 existing-capability families and 14 proposed-feature families).
- **1,529 prototype connections** include contextual navigation; this count is not a count of distinct tested journeys.
- All **212 API entries** below have a UX or protocol-reference mapping. Checked API entries mean traceability only, never implemented integration.
- Link-first verification, invitation and recovery designs are the default. Email code entry and passwords are explicit fallbacks; MFA challenges remain where required.
- User creation/invitation, access review, role assignment/revocation, effective permissions, groups, policies and administrative lifecycle actions have dedicated screens.
- **Frontend implementation is not complete.** This design work has not wired these new screens to APIs, implemented link-token contracts, or run application end-to-end tests.
- **Design completion is also not claimed:** every family has frames, but the remaining dialog details, error branches, input interactions, mobile/theme adaptations and accessibility QA still need their independent checks below. Proposed capabilities remain proposals until implemented.
- Structural inspection found no content outside screen bounds. Representative identity, mobile, platform, access, policy and integration screens were visually reviewed; that is not a visual review of every frame.
- Foundations include 54 variables, light/dark semantic aliases, 7 typography styles and 35 initial component variants. Table/dialog/card interaction families still need further component work.

### Capability handoff notes

- Email verification links correspond to the verification-token contract; OTP is only an alternate UI when an appropriate fallback contract exists.
- Reset-link redemption, passwordless account creation, invitation activation/session completion and cross-device completion may require contract extensions. Their screens describe the target experience, not evidence that these extensions exist.
- Email-link landing pages preserve purpose, tenant and validated destination. An intentional continuation avoids consuming a credential through a mail scanner’s GET/prefetch.
- Never use a sign-in link as a verification, password-reset or invitation token interchangeably. Do not silently change the active account.
- Shared failure/denied/conflict/unsaved/loading screens are reference patterns. Their presence does not check off each feature’s concrete state behavior.

## End-to-end journey coverage

- [ ] **J01 First run** — Uninitialized platform → setup token/admin → initialized result → real session or sign-in → permitted console; invalid token, race, service unavailable.
- [ ] **J02 New organization** — Workspace/owner details → slug check → registration → verification/sign-in as required → correct tenant; slug taken, rate limit, retry same idempotency key.
- [ ] **J03 Password login** — Tenant resolve → email/method → password → verified/no-MFA destination; wrong password, locked account, disabled tenant, unverified email.
- [ ] **J04 MFA login** — Password → actual supported challenge → success; backup code, invalid code, exhaustion, expired temp token, restart without a false session.
- [ ] **J05 Enforced enrollment** — Password/magic link/passkey result → required enrollment → verify → save recovery → completed session or fresh login; token expires, cancel, policy mismatch.
- [ ] **J06 Passwordless** — Magic-link request → email → verification → MFA/enrollment if required → original destination; used/expired link and resend.
- [ ] **J07 Passkey** — Start → external browser prompt → assertion → server result → correct next branch; unsupported browser, cancel, expiry/replay rejection.
- [ ] **J08 Social login/link** — Provider → callback claim → real session claims → MFA/verification/destination; cancellation, provider disabled, link confirmation expiry, existing account.
- [ ] **J09 Password recovery** — Request → generic acknowledgement → email-bound code/new password → success → fresh login; wrong code, exhausted attempts, reuse/policy failure.
- [ ] **J10 Invitation** — Admin invite → email → validate → accept → sign-in/verification → invited tenant; existing account, used/expired link, wrong active tenant.
- [ ] **J11 Workspace change** — Open organization menu → target → target tenant sign-in → confirmed session → fresh scoped data; denied/revoked membership, cancel back to source.
- [ ] **J12 Personal security** — Add authenticator/passkey → verify → recovery; regenerate codes invalidates old codes; remove factor/disable all → recent sign-in if required → explicit reconfirmation.
- [ ] **J13 Sessions/account** — View sessions → revoke another/others/all → truthful result; edit profile; change password; delete account → recent sign-in → confirm → session ended.
- [ ] **J14 People operations** — Filter/page → invite/detail → supported edit/status/lock/reset/delete → success/error → refreshed list; denied and missing user; partial bulk outcome.
- [ ] **J15 Role/permission** — Create role → add permission → assign with names/expiry/reason → effective permissions → revoke; system role, invalid permission, denied.
- [ ] **J16 Group/policy** — Create group → add members → attach policy → simulate allow/deny → detach/delete; JSON error, hierarchy constraint, explicit-deny result.
- [ ] **J17 Application integration** — Create public/confidential client → credentials acknowledgement → URI/origin configuration → integration guidance → rotate/delete; public client has no client secret.
- [ ] **J18 OAuth/SAML** — App → authorize/SSO → tenant sign-in → consent where supported → validated return; deny, expired request, wrong tenant/browser. Include the complete consent UX.
- [ ] **J19 Provisioning** — SCIM create/copy/revoke token; LDAP create/edit → test → sync → result; failed bind, expired token, failed sync. No fabricated job monitor.
- [ ] **J20 Webhooks** — Endpoint create/edit → test → delivery inspect → redeliver → outcome → rotate secret; failure/retry/denied/deletion.
- [ ] **J21 Branding/settings** — Edit draft → preview → validate → save → reload; upload failure, poor contrast guidance, unsaved navigation, unsupported policy action.
- [ ] **J22 Audit investigation** — Tenant event filter → detail → export → file; no results, forbidden, server/export error; platform activity stays separately scoped.
- [ ] **J23 Platform operations** — Tenant create → inspect → update/suspend/restore/delete; team add/remove; maintenance/settings; deny non-operators and prevent UI-only privilege assumptions.
- [ ] **J24 Context and outage** — Unknown/custom/subdomain tenant; session restored/expired/revoked; 403 direct link; backend unavailable/partial outage; return-to login then original safe destination.

- [ ] Proposed capabilities N01–N14 each have entry, validation, completion, cancellation and recovery paths.
